# Packaging

These files prepare distributions from the project. No public repository,
crates.io release, AUR listing, or maintained package service has been assumed.
Set the real repository URL and release maintainer before publishing. Commit
`Cargo.lock` and preserve dependency license notices in binary distributions.

## Local Cargo install

```sh
cargo install --path . --locked
cargo install --path . --locked --no-default-features --features lua54
```

The two alternatives install the same `cybar` binary; choose one. Once a
maintainer publishes the crate, `cargo install cybar --locked` will use the
vendored default LuaJIT runtime. Until then, use the checkout.

## Debian

Install a Rust toolchain, C build tools, `pkg-config`, `binutils`, `dpkg`, and
Python 3.11 or later. The helper builds one runtime and reads the package metadata
in `Cargo.toml`. It uses `cargo-deb` when installed, otherwise the bundled Python
packager:

```sh
bash packaging/deb/build.sh luajit
bash packaging/deb/build.sh lua54
```

Packages are written under `target/debian/`. LuaJIT uses package name `cybar`;
the Lua 5.4 variant is `cybar-lua54` and conflicts with and provides the default.
The binary, Lua examples, compressed man page, license, README, build instructions,
documentation tree, project assets, screenshots, and shell completions are included.
Both packages use `/usr/share/doc/cybar/` so the README's relative asset links work.
The helper does not install either package or start the bar. Inspect the resulting
archive with `dpkg-deb --contents` and `dpkg-deb --info` before distributing it.

To package already built binaries without rebuilding or installing `cargo-deb`:

```sh
python3 scripts/package-deb.py --runtime luajit --binary dist/cybar-luajit --out dist
python3 scripts/package-deb.py --runtime lua54 --binary dist/cybar-lua54 --out dist
```

The input must be a native Linux/glibc executable compiled with the named runtime.
The local packager reads required GLIBC symbol versions with `readelf` to set the
minimum `libc6` dependency and includes `libgcc-s1`. It rejects additional shared
libraries requiring unconfigured dependencies. Package architecture comes from
`dpkg --print-architecture`, with a host architecture fallback; cross packaging
requires an appropriate builder. Completions are generated by the supplied binary.
Archives contain root-owned files, normalized timestamps, reproducible manual
compression, and MD5 file checksums. `SOURCE_DATE_EPOCH` controls archive timestamps
and defaults to zero. The helper checks control fields, ownership, required paths,
the extracted binary, and manual before writing the archive, then prints its SHA256.
Existing `.deb` outputs are preserved; select a new output directory to rebuild.

## Arch / AUR

Four standalone templates are provided:

| Directory | Source | Runtime |
| --- | --- | --- |
| `aur/cybar` | Git tag `v<pkgver>` | LuaJIT |
| `aur/cybar-git` | Current repository commit | LuaJIT |
| `aur/cybar-lua54` | Git tag `v<pkgver>` | Lua 5.4 |
| `aur/cybar-lua54-git` | Current repository commit | Lua 5.4 |

All variants provide the `cybar` binary and conflict with the other variants.
They require Arch's usual `base-devel` build environment plus Rust and Git.
They install documentation, example configuration, man page, license, and
completions generated by their built binary.

`CYBAR_REPOSITORY` configures the Git source. Its default
`https://example.invalid/cybar.git` is deliberately an unusable placeholder.
Replace it with the actual source repository before running makepkg:

```sh
cd packaging/aur/cybar
export CYBAR_REPOSITORY=https://your-host/your-user/cybar.git
makepkg --printsrcinfo > .SRCINFO
makepkg -s
```

For a published AUR recipe, bake the verified repository URL into the file,
update the maintainer/version, and regenerate `.SRCINFO`. Release templates
fetch a version tag; Git sources use makepkg's `SKIP` checksum convention, so
the release process should authenticate the source/tag. The repository URL above
is an instruction placeholder, not a Cybar project URL.

## Release verification

Build and test both runtime features, validate shipped configs, run the isolated
X11 integration test, and run `cargo deny check` for both feature graphs. Inspect
the packages before upload. Verify the chosen source repository/tag, package
conflicts, and required notices. Real-desktop compatibility testing should include
the intended WMs, tray applications, DPI values, and smooth-scroll hardware.
